# 上下游 CI 联合审计（2026-10-22）

范围：`HandSonic/1Panel-Build-v2` 与本仓库的版本发现、上游输入认证、产品矩阵、重跑、安装升级验收、发布和恢复。

## 日志确认的问题

下游运行 #544（39795187210）解析到 v2.4.1 时，上游尚未发布该版本，七个 custom 分支明确失败。10 个 official/enterprise 分支已经成功上传，但 `publication_prepare` 随后因 Jobs API 尚未显示终态而抛出 `Nonterminal, cancelled or skipped package branch cannot authorize publication`。这使独立成功的产品也无法进入安装验收。

修复后的矩阵只把打包命令失败作为可独立记账的产品失败。每个分支都上传绑定本次计划与真实执行 attempt 的结果记录；失败记录不携带半成品。汇总依赖原生矩阵完成，并独立验证成功产物，API 只用于认证作业身份。报告、上传及其他基础设施失败继续阻止汇总。部分产品合格可独立发布，但最终 `publication_status` 将不完整的请求矩阵标红。

## 其他确认并修复的问题

| 问题 | 修复 |
| --- | --- |
| 下游不识别上游 `outcome_source: package-step`，仍把产品结果等同于 compile 作业结论 | 按新契约校验 compile 成功、显式产品账本及最终 matrix_status；旧契约保留原规则 |
| verified-CI 固定匹配不带 attempt 的产物名 | 同时严格接受旧名称和真实上传 attempt 对应的新名称，并绑定实际上传日志 |
| 重跑时复制的成功作业被误认为新的生产者 | 认证完整执行元数据，区分继承副本和真实新执行；旧成功不能覆盖新失败 |
| 合法上游架构子集被整个拒绝 | 认证明确请求的架构及其结果；未提供的包只影响下游对应产品，不伪造上游结果 |
| 候选输入、native 取证及最终发布再次依赖当前 run 的 API 终态 | 当前 run 使用 DAG 绑定的计划、artifact ID、receipt SHA 和真实成功证据；跨 run 历史认证保持严格终态校验 |
| schedule/dispatch 可以绕过源代码回归 | 两个 planner 直接依赖成功的 regression |
| `docs/**` 把运行时恢复 JSON 也排除在 CI 外 | 仅忽略 Markdown 文档，JSON 仍触发回归 |
| 上传成功后立即读回可能看不到新附件或其 digest | 校验并保留上传回执，有限重试 GET；不重复 POST，错误身份、字节或既有资产变化立即失败 |

上游还修复了 PR 合并后 `run.pull_requests` 变空导致历史 CI 产物不能晋升的问题。恢复只依赖认证的成功 checkout 日志、已合并 PR 的冻结 base/head 和真实 merge parents，不单凭文件名或 Git 对象放行。

## 验证与覆盖边界

真实上游 v2.4.1 amd64 包的 API 大小与 SHA、内嵌源码契约、前端锁、完整压缩包、官方配置、GeoIP 原始资源和安装接口均通过下游静态校验。上游历史运行 #654 的原始证据也已重放，七架构认证通过。

实际安装门禁覆盖 amd64/arm64 的 fresh/existing Docker；社区产品另有真实前驱升级与回滚验收。其他架构为静态验证，enterprise-original 为官方原始字节验证。静态检查不等同于所有架构已通过原生安装，测试环境也未实施网络隔离。

完整回归和新的 hosted 构建结果以本次 PR 与后续 Actions 运行记录为准。公开资产写入保持原有逐产品准入、同版本锁与只补缺失策略；冲突字节不自动覆盖或删除。
